# The Originally Ideated Product

This document records the product as originally conceived, independently of what any
particular version ships. It exists so the full intent survives the scope cuts made for
v1 and can be rebuilt from first principles later.

Sources: [test-case-generator-prd.docx](test-case-generator-prd.docx),
[test-case-generator-technical-specification.docx](test-case-generator-technical-specification.docx),
both generated by [../scripts/generate_product_docs.py](../scripts/generate_product_docs.py),
which is the prose source of record.

Durable product truth lives in [../PRODUCT.md](../PRODUCT.md). This document is the
historical and architectural companion to it.

## 1. The problem

QA teams receive feature PRDs late in the lifecycle and must translate them into coverage
plans under time pressure. That process is document-heavy, inconsistent across reviewers,
and dependent on individual domain memory to remember validation, regression, permission,
integration, and observability scenarios.

Stated intent: **shorten first-draft creation and reduce missed coverage — not replace
human QA judgment.**

## 2. Intended users

- **Primary:** QA engineers and SDETs drafting and owning a feature's coverage plan.
- Secondary: product analysts, engineering managers reviewing feature readiness, release
  management.

The primary user is the design tiebreaker. See [../PRODUCT.md](../PRODUCT.md).

## 3. Intended benefits

- Reduce first-draft QA coverage preparation from hours to minutes.
- Make PRD interpretation consistent across reviewers and teams.
- Surface missing edge cases, implied dependencies, and likely regressions earlier.
- Preserve team knowledge in uploaded documents rather than individual memory.
- Produce structured output that can be exported to test management tooling.

> These are stated goals from the project's own PRD, not measured results. No benchmark
> has been run. Do not present them as evidence.

## 4. Scope boundary

Explicitly **out of scope** for the product as ideated:

- full test management
- test execution tracking
- defect lifecycle workflows

The product drafts feature-specific coverage. It is not a test management system.

## 5. The intended workflow

From the original concept note:

1. User lands on the QA workspace and uploads a PRD plus optional supporting documents.
2. Frontend sends all files to the backend in a multipart request.
3. Backend extracts text from PDF, DOCX, and text-like formats, trimmed to safe model limits.
4. Gemini analyses the PRD as primary source, uses supporting documents as secondary
   context, and returns a structured feature summary, assumptions, risks, and prioritized
   test cases.
5. Frontend renders the suite with criticality markers and expandable steps per case.
6. User reviews, and iterates by replacing the PRD, adding context, or removing noisy files.

## 6. Intended screens

| Screen | Purpose |
|---|---|
| QA Workspace Landing | Upload actions, flow explanation, contextual summary of what is attached |
| PRD Upload Flow | One PRD per run; replacing resets stale generated results |
| Knowledge Base Upload Flow | Multiple supporting documents, individually removable |
| Analysis in Progress | Loading state with progress messaging; attachment status stays visible |
| Generated Test Case Review | Summary first, then risk/assumption/source context, then cases with expandable steps |

Stated error and edge-state expectations:

- Missing PRD must block generation with a clear corrective message.
- Parse failure must identify which file failed and why.
- Model error or empty output must preserve uploaded context and allow retry **without
  forcing re-upload**.

## 7. Intended architecture

Browser client → API server → LLM provider.

| Layer | Responsibility |
|---|---|
| Frontend | Interaction and display; uploads files, renders suite, handles loading and error states |
| API layer | Transport and validation; routes, CORS, JSON responses, health endpoint, multipart handling |
| Parsing layer | Text extraction — `pdf-parse` for PDF, `mammoth` for DOCX, direct read for TXT/MD/CSV/JSON/RTF |
| Inference layer | Prompt assembly, structured output request, schema-constrained generation |
| Shared contract | `GeneratedSuite` types shared by client and server |

### The MVP was specified as stateless

This matters for understanding v1. The original technical specification states plainly:

> "The MVP is intentionally lightweight and stateless."
>
> "The live MVP does not yet persist runs, but the following data model should be used when
> the system graduates from transient processing to durable storage."

In the original design, knowledge-base files were sent as a **repeated `knowledgeBase` file
field on the same `POST /api/generate-test-cases` request** as the PRD. There was no
server-side retention.

Server-side SQLite persistence was added later, ahead of the original plan. **v1 therefore
returns to the originally specified architecture**, rather than cutting below it.
See [decisions/0001-browser-scoped-persistence.md](decisions/0001-browser-scoped-persistence.md).

## 8. The intended durable data model

Proposed for "when the system graduates to durable storage." **Not implemented.** Recorded
here in full so it can be built without re-deriving it.

Relationships:

- A feature has many documents and many generation runs.
- A generation run belongs to one feature and produces many test cases.
- A generated test case belongs to one generation run and has many ordered steps.
- Documents are tagged by type so the PRD stays distinguishable from supporting content
  during audits and reruns.

### `features`
| Field | Type | Description |
|---|---|---|
| id | UUID | Primary key for the feature workspace |
| title | VARCHAR(255) | Human-readable feature or PRD title |
| status | VARCHAR(32) | draft, analyzed, archived |
| created_at | TIMESTAMP | Record creation |
| updated_at | TIMESTAMP | Last modified |

### `documents`
| Field | Type | Description |
|---|---|---|
| id | UUID | Primary key |
| feature_id | UUID | FK to feature workspace |
| document_type | VARCHAR(32) | `PRD` or `KNOWLEDGE_BASE` |
| original_filename | VARCHAR(255) | Uploaded file name |
| mime_type | VARCHAR(128) | Uploaded content type |
| storage_path | TEXT | Pointer to object storage or managed file store |
| extracted_text | LONGTEXT | Normalized parser output |
| excerpt | TEXT | Short preview for UI |
| parse_status | VARCHAR(32) | `PARSED`, `FAILED`, `PARTIAL` |
| created_at | TIMESTAMP | Record creation |

### `generation_runs`
| Field | Type | Description |
|---|---|---|
| id | UUID | Primary key per generation attempt |
| feature_id | UUID | FK to feature workspace |
| model_name | VARCHAR(128) | LLM used for the run |
| prompt_version | VARCHAR(64) | Prompt template version, for traceability |
| status | VARCHAR(32) | `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED` |
| summary | TEXT | Generated feature summary |
| risks_json | JSON | Highlighted risks |
| assumptions_json | JSON | Model assumptions |
| source_highlights_json | JSON | Source references shown in UI |
| created_at | TIMESTAMP | Record creation |

### `generated_test_cases`
| Field | Type | Description |
|---|---|---|
| id | UUID | Primary key |
| generation_run_id | UUID | FK to generation run |
| title | VARCHAR(255) | Short test case title |
| criticality | VARCHAR(16) | Low, Medium, High |
| rationale | TEXT | Why the case matters |
| coverage_area | VARCHAR(128) | Logical category |

### `generated_test_steps`
| Field | Type | Description |
|---|---|---|
| id | UUID | Primary key |
| generated_test_case_id | UUID | FK to generated test case |
| step_order | INTEGER | Display order |
| instruction_text | TEXT | Actionable tester instruction |

> Note: `prompt_version` and `model_name` on `generation_runs` are the traceability fields
> the current implementation lacks. Preserve them in any rebuild — without them, a suite
> cannot be attributed to the prompt that produced it.

## 9. Intended API surface

### `GET /api/health`
Uptime and readiness check. No request body. `200 OK` with `{ "status": "ok" }`.

### `POST /api/generate-test-cases`
The primary endpoint.

| Aspect | Specification |
|---|---|
| Method | POST |
| Content type | `multipart/form-data` |
| Required file field | `prd` (exactly one) |
| Optional repeated file field | `knowledgeBase` (zero or more) |
| Upload strategy | Memory-backed, with file count and size limits in Multer |
| Supported parsing | PDF, DOCX, TXT, MD, CSV, JSON, RTF |

Files are parsed server-side, never in the browser.

**Success response**

| Field | Type | Description |
|---|---|---|
| featureName | string | Generated human-readable feature title |
| shortSummary | string | Concise feature description from the PRD |
| risks | string[] | QA risks and blind spots |
| assumptions | string[] | Model assumptions and inferred constraints |
| sourceHighlights | string[] | Key references from source documents |
| cases | GeneratedTestCase[] | Test cases with criticality, rationale, coverage area, steps |

**`GeneratedTestCase`**

| Field | Type | Description |
|---|---|---|
| id | string | Stable identifier within the response |
| title | string | Short test case name |
| criticality | `Low \| Medium \| High` | Priority marker |
| rationale | string | Why the case matters |
| coverageArea | string | Logical grouping |
| steps | TestStep[] | Ordered execution steps |

**Failure modes**

- `400` — PRD missing, or unsupported file type
- `500` — unexpected parse failure, unusable model output, or missing API key
- Error shape: `{ "error": "human-readable message" }`

## 10. Ideated roadmap beyond MVP

From the original PRD's own forward look, plus items added since:

- persistence, run history, and export
- collaboration features
- export to CSV, XLSX, or test management tools *(now a binding constraint — see PRODUCT.md)*
- tag, group, or archive previous runs
- authentication and multi-user storage
- richer ingestion and OCR for image-based PDFs
- prompt/version audit history per run
- editing and saving curated test cases after generation

## 11. What the ideated product does not answer

Recorded so a future rebuild does not mistake silence for a decision:

- No multi-tenancy model. "Product for other companies" is the stated destination
  (PRODUCT.md), but no tenant isolation, billing, or org model was ever specified.
- No chosen export target. Jira, TestRail, and Xray are named as candidates only.
- No stated position on whether human approval is mandatory before a suite is used.
  The PRD says the tool does not replace human judgment; that was not made binding.
- No accessibility standard committed for the product itself.
- No pricing, licensing, or commercial model.
